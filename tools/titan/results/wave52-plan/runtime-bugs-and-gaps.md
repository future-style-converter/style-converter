## 3. Mechanism, with file:line evidence

**7(b) — iOS nowrap path never resolves a percent flex-basis.** The wire is a bare number (`{"type":"FlexBasis","data":50}` in the per-test IR). `FlexboxExtractor.swift:238-240` maps `.double/.int → .percent`; `ItemPlacement.swift:158` stores it as `FlexClaim.basisPercent` (`:57`). The wrap path consumes it (`FlowLayout.swift:211-214`: `maxMain * pct / 100`). The nowrap path does not: `CSSFlexLayout.swift:262` builds every item as `basis: claim.basisPx ?? ideal.main` — a percent claim falls through to the intrinsic size, 0 for an empty div. Android passes (0.9984) because `ItemPlacementExtractor.kt:54` (retro R2) plus its consumer resolve the percent; web emits the longhand.

**M1 — a DECLARED body `margin-left` never reaches the body's children on any composed canvas.** The extractor emits html+body as ONE synthetic `meta.role: body-root` component whose element children are **siblings**, not descendants (`tools/titan/extract-fixture.mjs:9210-9211` "SIBLINGS of the body-root, they are not its descendants on any platform"; `:9251` "a non-inherited root declaration (`background`, `margin`, `contain`, …) changes nothing for the children"). The three canvases read the body-root only for background and PADDING: web `apps/web-harness/src/ui/ComposedCaptureGallery.tsx:492 resolveCanvasPadding` (spent on the ICB div `:757-763`), Android `apps/android-harness/app/src/main/java/com/styleconverter/test/screenshot/ScreenshotCaptureScreen.kt:1341 resolveComposedCanvasPadding` (call `:1521`), iOS `apps/ios-harness/StyleConverterTest/Screenshot/CaptureCanvas.swift:563 resolvedPadding`. No margin twin exists. The ref keeps the author margin because `tools/titan/capture-browser-ref.mjs:490` injects `:where(html, body) { margin: 0; … }` at specificity 0 and `body { margin: 0 0 0 200px }` (0,0,1) wins — the ref is the CSS-correct picture. The VERTICAL half leaks through by accident: the empty body-root box's top/bottom margins collapse through (CSS 2.1 §8.3.1), so `collapsed-border-vertical-rtl-overflow` (margin 60) has web ink rows 76–295 = ref, but cols 16–197 vs ref 76–257. `background-attachment-margin-root-001/002` (f 0.45/0.34 ×3) are NOT this family: their margin IS honoured (ink starts at 66 = 16+50) and the defect is root-background canvas propagation (css-backgrounds-3 §2.11.2) on a sized root.

**M2 — both natives turn a negative flex-item margin into a paint offset only.** iOS `StyleEngine/spacing/MarginApplier.swift:108-136`: positive sides → outer `.padding`, negative sides → `OffsetIf` (`:117-118` "here only the self-offset is reproduced"); `CSSFlexLayout.swift:246-266` measures `sub.sizeThatFits` (50) and `mainOffsets` (`:128-152`) advances `cursor += s + gap` — the −150 never enters §9.7. Compose `spacing/MarginApplier.kt:176-206`: `absolutePadding` for positive, `Modifier.offset(x = negX…)` (`:206`) for negative; the nowrap container is a Compose `Row` (`core/renderer/ComponentRenderer.kt:2213` for `FlexContainerKind.Row`, `:2508` legacy `FLEX_ROW`) whose children advance by their measured 50. css-flexbox-1 §9.2 step 3 defines the *outer* hypothetical main size = size + margins and §9.7/§9.5 sum and place by outer sizes: One's outer size is −100, so Two starts 100 px left of the content edge and the six items fit the 200-px container exactly (6·50 + 5·10 − 150 = 200), which is what the ref paints.

**M3 — Compose `Row` cannot let shrink-0 items overflow.** `FlexboxApplier.kt:168-182` builds `Arrangement.spacedBy(gap, Alignment.Start)`. Compose's `Row` measures child i with `maxWidth = remaining` (Four → 20, Five/Six → 0), `spacedBy.arrange` clamps `position = min(occupied, total − size)`, and Compose centres an over-constrained child in its slot (`(20−50)/2 = −15`, `(0−50)/2 = −25`). Predicted x from that model: Four 180−15 = 165, Five/Six 200−25 = 175 relative to content x=18 → **183 / 193 / 193 — the measured runs on both 008 and 027**. CSS (§9.7 with all shrink factors 0, §9.5 start-packed, css-overflow-3 §2 visible) overflows the end edge instead. The gap-decoration segments then follow the squeezed slots, so three of five rules vanish.

**7(a′) — band edges are not pixel-snapped.** iOS `GapDecorationSegments.swift:20-23` centres the rule in the gap; `GapDecorationsPainter.swift:153/157` fills `Path(seg.rect)` unsnapped, so a 5-px rule centred in a 10-px gap starts at x.5 → the 255,128,128 half-pixels. Kotlin `GapDecorationBands.kt:170-172` rounds line extents to Int (why Android's main-axis rule is crisp) but `GapDecorationPainter.kt:86` draws `Offset(r.left, r.top)` unsnapped for the cross bands, and the Int share `+1 to the first remainder lines` moves 046's second band +1. ## 4. Proposed fixes (CSS-correct behaviour cited)

1. **7(b) — `CSSFlexLayout.swift:262`**: `basis: claim.basisPx ?? claim.basisPercent.flatMap { available.map { a in a * $0 / 100 } } ?? ideal.main`. css-flexbox-1 §9.2 step 3.A: a definite percent flex basis resolves against the container's inner main size; §7.2.3: an indefinite container makes it `content` — exactly the existing `available == nil` fallthrough. Abspos children must stay out (§4.1) — check they are not subviews of the layout.
2. **M1 — a `resolveCanvasMargin` twin on all three canvases**, same shape as the padding resolver (concrete px only; `auto` / `em` / `%` leaves keep 0). Spend it on the in-flow root stack INSIDE the ICB div (web: the block-flow div holding the roots; Android: the composed column; iOS: `CaptureCanvas` VStack), never on canvas-hoisted abspos/fixed roots — CSS 2.1 §10.1 anchors those at the ICB, and a static body is no containing block, so the margin moves only in-flow content (the same lesson as CAL-RC1's padding). Vertical: the flow stack must be a BFC (`display: flow-root`, as the ref injects) so the body margin no longer collapses through — replace today's accidental collapse-through with the declared value; negative `margin-top` (s-11-1-1b-005: −15) needs a margin, not a padding, so put it on the flow wrapper.
3. **M2 iOS — outer main size in `CSSFlexMath`**: add `mainMarginStart/End: CGFloat` to `ItemPlacement.FlexClaim` (fill in `ItemPlacement.swift` from the MarginConfig), carry `outerDelta = min(0,start) + min(0,end)` into `ItemInput`, sum outer sizes in `mainSizes` and advance `cursor += s + outerDelta + gap` in `mainOffsets`. Positive margins are already inside the measured frame (outer `.padding`), and the item's own `.offset` already paints the border box at cursor − 150, so ONLY the advance changes (css-flexbox-1 §9.2 step 3, §9.7 step 1, §9.5).
4. **M2+M3 Compose — one change**: route nowrap `FlexContainerKind.Row`/`Column` through a custom `Layout` (`layout/flexbox/FlexNowrapLine.kt`, sibling of `FlexWrapRow`) that measures children with an unbounded main-axis constraint, sums outer hypothetical sizes (§9.2 step 3, incl. negative margins), runs §9.7 with the existing `FlexSizeResolver`, and places sequentially without clamping (§9.5; css-overflow-3 §2 visible overflow). `Row` stays for the item-less/legacy cases. `columns/GapDecorationHook.kt` must keep receiving the placed frames.
5. **7(a′) — snap band rects** in `GapDecorationsPainter.swift` (before `ctx.fill`) and `GapDecorationPainter.kt:86`: `start = round(start)`, `end = round(start + thickness)` (Chromium's `PixelSnappedIntRect`); and make `GapDecorationBands.kt`'s share distribution match Swift's `leftover / n` BEFORE rounding so the two natives agree (a′'s open parity item).
