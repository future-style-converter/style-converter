## 3. Mechanism, with file:line evidence

### A. The 16-px overrun = the ICB clip is missing on all three composed canvases

The reference is **rendered in a 358-px viewport and padded in image space**: `tools/titan/capture-browser-ref.mjs:310` `REF_RENDER_WIDTH = CANVAS_WIDTH - 2 * CANVAS_PAD_PX`, `:920`/`:928` `page.setViewport({ width: REF_RENDER_WIDTH, … })`, `:570` `padPngBuffer` memcpy's the 16-px frame around the screenshot. Anything laid out past content x=358 is scrollable overflow outside the viewport and is never in the PNG — the ref's right edge of ink is image x=373 by construction, and the frame columns 0..15 / 374..389 are always the uniform pad colour.

The runtimes' containing block is already right (358): web ICB div `apps/web-harness/src/ui/ComposedCaptureGallery.tsx:758` (`data-capture-icb`) with `composedIcbStyle` `:942-953` (`width: 100%` inside the 16-px-padded 390 canvas); Android `apps/android-harness/app/src/main/java/com/styleconverter/test/screenshot/ScreenshotCaptureScreen.kt:1766-1774` (`LocalContainingBlock … widthPx = (canvasWidth - canvasPadding.horizontal)`), in-flow `Column(… .padding(start=canvasPadding.left …))` `:1867`; iOS `apps/ios-harness/StyleConverterTest/Screenshot/CaptureCanvas.swift:780` (`.frame(maxWidth: Self.width - pad.leading - pad.trailing …)`), `:96` (`rootContainingBlock: width - padding * 2`). A declared `width: 400px` (gaps-040 IR: `{"type":"Width","data":{"type":"length","px":400}}`) or `width: 63.1ch` (`original: {v: 63.1, u: "CH"}`, resolved by the runtime against the 13-px monospace advance ≈ 492 px) legitimately overflows that ICB — in Chrome too.

What differs is **where the crop happens**: web `composedCanvasStyle` `:878` `overflow: 'hidden'` sits on the **390-px outer div**, and the ICB div is deliberately `display: 'flow-root'` with no clip (`:949`, banner `:938-940` "adds no clip"); Android's `ComposedCaptureCanvas` (`:1455-1900`) has no clip at all outside the root-`clip-path` branch (`:1722`), so the Column and the `CanvasRootHoist.Host` (`:1831`) overlay paint into the frame; iOS `ComposedCaptureCanvas` (`:277-870`) has no `.clipped()` (the per-component canvas has one at `:178`). Result: everything between ICB x=358 and canvas x=390 is visible in the capture and invisible in the ref — a 16-px band of ref-frame colour vs capture ink, identical on web/iOS/Android (§2: 1664 px on each platform for gaps-040). Left frame is the mirror image (negative x — 84 cells, §5).

### B. The clip/mask pair = the reference harness zeroes the UA body margin on the reference only

`capture-browser-ref.mjs:490` `canvasFrameCss()` injects `:where(html, body) { margin: 0; padding: 0; background: … }` into the **reference** page (`:6`: the `*-ref.html` is what is rendered, `resolveRefPath :621-641`). `clip-path-paddingBox-1d.html` declares `body { margin: 0 }` and draws a 100×100 green box with an 8-px red border clipped to `padding-box`; its match `reference/green-100x100.html` is a bare 100×100 green div that relies on the **UA default `body { margin: 8px }`** to land at the same (8,8). Zero-specificity `:where()` beats the UA sheet but loses to the test's own `body { margin: 0 }`, so under the injection Chrome puts the ref's green at (0,0) → image (16,16), while Chrome-on-the-test (and all three runtimes, which render the IR's explicit `MarginLeft/Top: 0px` on the body-root and the 8-px border) puts it at (8,8) → image (24,24). The runtime's picture is CSS-correct (css-masking-1 §5 + css-shapes-1 `padding-box`); the ref is displaced by the very 8 px the injection removed. `contentBox-1d/-1e` are the same shape (border 4 + padding 4).

## 4. Proposed fixes, CSS-correct behaviour and spec

**Fix A — horizontal viewport crop at the ICB, all three composed canvases (harness only, zero runtime layout code).**
- Web: `composedIcbStyle` gains `overflowX: 'clip'` (nothing on y). css-overflow-3 §3.1: `clip` clips at the overflow clip edge (padding edge + `overflow-clip-margin: 0px`, i.e. exactly 358) **without** making the box a scroll container or changing formatting context; §3.2: the pair `overflow-x: clip; overflow-y: visible` is preserved as specified (the visible→auto coercion applies only when the other axis is neither visible nor clip). Vertical must stay visible: the ref's second viewport is `max(scrollHeight, 568)` so the ref never crops the bottom, and cropping at the ICB's in-flow height would hide abspos content the ref shows.
- Android: inside the `drawWithContent { graphicsLayer.record { … drawContent() } }` at `ScreenshotCaptureScreen.kt` ~`:1700-1706`, wrap `drawContent()` in `clipRect(left = frameLeftPx, top = -BIG, right = size.width - frameRightPx, bottom = +BIG)`, positioned AFTER `.background(canvasBackground)` (`:1725`) so the frame keeps the propagated body colour; this one clip covers both the Column and the `CanvasRootHoist.Host` overlay. Put the rect arithmetic in a pure helper beside `composedIcbExtentDp` (`runtimes/compose/src/main/java/com/styleconverter/runtime/core/renderer/WptCaptureMode.kt:214`) so it is JVM-pinnable.
- iOS: a `Shape` returning the rect x∈[16, 374), y∈(−∞, +∞) applied with `.clipShape` to a group that contains the in-flow VStack chain **and both** `FixedHoistOverlay` attach points (`CaptureCanvas.swift:811` behind, `:867` above), attached before `.background(canvasBackground)`; today the overlays are attached outside the content chain, so the seam is moving them inside one clipped group (`runtimes/swiftui/Sources/StyleConverterRuntime/Renderer/FixedHoist.swift:368-400` — `canvasFrame` keeps its meaning).
Rationale: CSS 2.1 §9.1.1 — the initial containing block has the dimensions of the viewport; the ref's viewport IS the ICB (`capture-browser-ref.mjs:180-182` "the viewport IS the content canvas"). The harness's frame is a picture frame around the viewport, not part of it.

**Fix B — make the reference-side margin injection test-aware (instrument change).** In `canvasFrameCss()` split the body half: when the TEST declares a body margin (probe the test page in the same headless Chromium: any `CSSStyleRule` with `document.body.matches(rule.selectorText)` whose style sets a `margin*` longhand, or an inline `<body style>` margin), inject `:where(html) { margin: 0 }` + `:where(body) { padding: 0; … }` and leave the body's UA margin in force — the exact condition the WPT pair was authored under (reftests are equivalent under the UA sheet, html.css `body { margin: 8px }`). Undeclared tests keep today's byte-identical sheet, so the two TEST-page bake paths that share it (`post-load-extract.mjs`, `bidi-bake.mjs`) are untouched. Refs are cached per TEST (`cachePathFor(wptRef, testRel, browserRev)` `:787-790`), so a per-test variant needs no key change beyond the standing rule: *"bump `CANVAS_REV`, re-freeze the affected refs, and adjudicate the resulting moves with the Calibration-gate recipe"* (BACKLOG "Instrument decisions pending"). Guard the PNG height: with an 8-px body margin the injected `min-height: 100vh` body makes scrollHeight 584 → a 616-tall PNG; the variant must inject `min-height: calc(100vh - 16px)` (or the builder pins that the four css-masking refs stay 390×600).
Rejected for wave 52: restoring UA 8 px on BOTH sides (bake `Margin*: 8px` into undeclared body-roots + drop the injection) — it moves 1285 of 1435 documents on both sides, re-wraps every prose line at 342 px, mis-renders `body { display: contents }` (`css-display/display-contents-text-only-001`, whose ref declares `margin: 0` for that reason), and is a whole-corpus re-freeze.
